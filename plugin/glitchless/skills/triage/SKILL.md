# Triage a game with Glitchless

You have two sources of truth:
- **Glitchless MCP** (`glitchless_*` tools without "live") — production telemetry from every player, aggregated.
- **The running game.** For a web game (Three.js, Phaser, Babylon.js, PlayCanvas): **WebMCP** (`glitchless_live_performance`, `glitchless_measure`, `glitchless_inspect_scene`, `glitchless_errors`, plus the game's own tools like `<game>_load_level`) in the user's browser right now. Tool names may carry a channel prefix (e.g. `localhost_5173-glitchless_measure`).
  If WebMCP tools are missing, ask the user to open the game, call the `_webmcp_get-token` tool and have them paste the token into the WebMCP widget. Work without it if they decline.
  For Unity, Godot, Unreal and GameMaker there is no WebMCP: `glitchless_playtest` with `command` runs a build with its autoplay bot and compares it with a baseline (steps 5 and 8), and for one measurement, run a build with `--glitchless-measure=SECONDS` (Unity: `--glitchless-out=FILE` writes the JSON; Godot prints one line starting `{"glitchless_measure"`; Unreal takes `-glitchless-measure=SECONDS`, prints that line too and writes `-glitchless-out`), started with the game's autoplay flags if it has them. The JSON has the same fields as `glitchless_measure`. In the Unreal editor, Unreal MCP with the Glitchless Toolset adds a `Measure` tool for Play In Editor (the instrument skill sets it up); confirm with a packaged Development build, since the editor compiles shaders on first use.

## Loop

1. **Rank.** Call `glitchless_triage` (24h by default). Pick the top finding, or the one the user named. Say in one line which one and why (severity × share of players affected). Findings marked `known` come last: the team has accepted them, so skip them unless the user asks. When the user says a finding is accepted and shouldn't come back in the weekly summary, offer `glitchless_mark_known` with their reason as the note. When an `error-*` finding is fixed in a release or isn't worth fixing (test devices, a driver bug), offer `glitchless_resolve_error` with their reason: it leaves triage until players hit it again in a newer version (test phones, bots and testers don't bring it back unless it was resolved with `all_sessions`). A finding with `came_back` is a resolved error that's back: say which version brought it back. An error with `no_players` (glitchless_get_error) was hit only by store test phones, bots, testers or dev builds: check it can happen on players' devices before changing code, and say so.
2. **Get the evidence.** Drill in by category:
   - performance → `glitchless_performance` with `level`: look at `hitch_context` (which gauges spike during hitches, which events precede them) and `slowest_recent_hitches[].loaf` (script attribution).
   - memory → `glitchless_performance` `memory` + `by_level.geometries_max`.
   - stability → `glitchless_get_error` with the fingerprint: stack, `location`, breadcrumbs.
   - design → `glitchless_player_funnel` with the level and `hotspots: true` for where players die, then without it for the level's funnel (`recent_rage_inputs` says where players mashed a key).
   - one session (a crash, a rage quit, a playtest) → `glitchless_session`: a summary level by level; `level` or `types` gives its events.
   - the game's own metrics (plays, purchases, the paywall, whatever it sends with `track`) → `glitchless_events`,
     with a `funnel` for drop-off between steps; `glitchless_dashboard` shows the pages and panels this game cares about.
   - **a Roblox game** connected to Roblox (Settings → Integrations → Roblox) → `glitchless_store` with `show: "vitals"` and
     `store: "roblox"`: Roblox's own crash rate and frame rate by place version and by platform next to Glitchless's,
     with a line where they disagree (a crash of the Roblox app itself, or out of memory, shows only on Roblox's side),
     and its D1, D7 and D30 retention. The Roblox SDK is anonymous, so "do players come back?" is answered by Roblox's
     retention, never by Glitchless's; `glitchless_revenue` with `source: "roblox"` has Robux, paying users and daily
     active users. Not connected: say that connecting it (with an Open Cloud key) brings these.
3. **Find the code.** Use the evidence as search keys: event names from `preceding_events` (e.g. the `glitchless.track('powerup')` call site), gauge names passed to `glitchless.setContext`, the error's function/file, level data near the hotspot's x range.
4. **Reproduce and baseline.** Web: load the level / trigger the effect with the game's tools, then run `glitchless_measure` for 5–10s. Unity, Godot and Unreal: build (Unreal: a packaged Development build), then run the measure flag on the level in question. Record p95, worst frame, draw calls, render and update CPU, peak gauges, the memory delta. For errors, reproduce and confirm with `glitchless_errors` (web) or the session in `glitchless_session`.
5. **Save a playtest baseline before touching code.** Call `glitchless_playtest` with `save_as: "baseline"`. The game's autoplay bot plays fixed-seed runs on the current code so you can prove later that your change made nothing else worse. A web game needs the game and Glitchless server running and Playwright in the project. For Unity, Godot, Unreal and GameMaker, pass `command` (what starts the build: `["godot", "--path", "."]`, or the exported build, rebuilt first) or set it in `glitchless.playtest.json`; each run starts the build with `--autoplay --seed=N` and the SDK's measure flag, and the game's autoplay mode has to keep playing for the whole measure (the error says how to add one if it has none). For Roblox, pass `engine: "roblox"` (and `studio` with several Studios open): it plays the place open in Studio over Studio's MCP server, with the scenario's params as Workspace attributes for the game's bot. If it can't run, say so, keep the measure JSON from step 4 as the baseline, and continue.
6. **Fix the root cause**, minimally and idiomatically:
   - many short-lived meshes → one `InstancedMesh`/`THREE.Points` or a pool; shared geometry/material; remove **and** `dispose()` when done
   - geometry growth per level load → dispose geometries/materials/textures on unload; share per-tile geometry
   - shader-compile hitches → `renderer.compileAsync(scene, camera)` during loading
   - unchecked lookups (`pool.find()` → undefined) → handle exhaustion gracefully, and apply game state (score) before anything that can throw
   - **Phaser:** objects and bodies that pile up → destroy them or recycle through a Group, one collider per group; `listeners` growing per restart → remove handlers on `shutdown` (scene events outlive a restart); `texture_upload` hitches → make textures once in the preloader; `game_loop_stopped` → the uncaught error stopped Phaser's loop for good, so make that callback fail safe
   - **Unity:** `gc` hitches → stop per-frame allocations (LINQ, string building, new lists); `object_spawn` → pool with `UnityEngine.Pool.ObjectPool`; mesh or material counts growing per level → `Destroy()` runtime meshes and materials, use `sharedMaterial`; `physics` → fewer rigidbodies, simpler colliders; `exception` → the rest of that `Update` never ran: guard the null or missing key
   - **Godot:** follow the finding's suggestion; it names Godot APIs
   - **Roblox:** follow the finding's suggestion (it names Roblox's fixes: StreamingEnabled, pooling instead of Clone and Destroy, anchoring, draw calls and shadows); a crash rate Roblox counts high on Phone or Tablet, with Glitchless seeing few crashes, is usually memory: lower texture and mesh detail, turn on StreamingEnabled, check `memory_mb` in `glitchless_session`
   - **Unreal:** `pso_compile` hitches → keep PSO precaching on, ship a bundled PSO cache (record with `-logPSO`), spawn first-use effects behind the loading screen; `-LogCmds="LogPSOHitching Verbose"` names each material; `gc` hitches → pool actors and objects instead of SpawnActor/NewObject per shot, keep short-lived data out of UObjects; `ensure` or `crash` → a UObject that is null or pending kill: test with `IsValid()`, keep it in a `UPROPERTY()`; `script` → a Blueprint read None: add an Is Valid node. With Unreal MCP connected, make Blueprint changes through it
   - **design findings** (a jump nobody makes): propose 1–2 concrete level-data changes with the numbers, and ask the user before changing game design.
7. **Verify.** Repeat the exact reproduction and measure again (web: reload and `glitchless_measure`; Unity, Godot and Unreal: rebuild and run the measure flag). Show a before/after table. On the web, drop a breadcrumb with `glitchless_annotate` (e.g. "agent: confetti → InstancedMesh, p95 48→15ms").
8. **Playtest the change.** Rebuild an engine game's export first, then call `glitchless_playtest` with no arguments (and the same `command`) to compare every scenario against the baseline. A FAIL means the work isn't done: read the regressions and new errors, fix them, and run it again. Report the verdict and the improvements table to the user.
9. **Version it.** Bump the patch version the game reports (`version` in `Glitchless.init`; Unity's `Application.version`; Godot's `application/config/version`; Unreal's `ProjectVersion` in `DefaultGame.ini`; Roblox's place version goes up by itself on each publish) so production data from the fix is separable, and tell the user to run `glitchless_compare_versions` (or open Versions in the dashboard) once players have played the new build. In a jam room, publish the new build to the room straight after (`glitchless_jam` with `action: "publish"`), so the next round of players gets the fix.

Never claim a fix worked without a measurement and a passing playtest; if you couldn't run either, say so and say what to watch in production.
